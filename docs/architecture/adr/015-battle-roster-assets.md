# ADR 015 — 战斗角色资源按阵容加载

状态：提议，未实施。

## 现有成本

在 c1011 配表已生成、场景尚未重绑的工作区，从已保存的 BattleScene 场景 YAML 读取五项序列化引用，用 `.meta` 的 GUID 回查源文件并按实际文件长度计数。

- 场景引用 11 个角色模型、33 个技能图、336 条演出依赖、6 个 FMOD bank 和 101 张界面 Sprite。去重后为 911 个直接引用文件、431.22 MiB。模型文件为 90.26 MiB，演出依赖文件为 110.95 MiB，6 个 bank 为 228.91 MiB。场景 YAML 自身为 0.21 MiB。
- 同期角色导入清单已有 12 名角色、1,105 个输出条目、478.27 MiB。清单同时包含角色实验室和共享资产。这里的 MiB 为工作区源文件尺寸，不能用于推算 GPU 显存、构建包体或 Player 驻留量。
- 当前 `ConfigureHudScene` 将目录中全部英雄的模型和所有技能依赖序列化到场景。开局实际准备的是选定阵容，但 Unity 已看到整个目录的直接引用。技能编辑器的独立预览也打开该场景资产。现有音频服务以 `TextAsset.bytes` 加载所有共享 bank，切成角色视觉包后仍需单独测量音频驻留。

## 拟议设计

1. 场景保留固定舞台、HUD、站位及共享表现。导入器通过已有角色目录、Luban 角色 ID 和带哈希的导入清单生成每个英雄的内容资产，包含模型、技能图及其依赖、肖像和技能图标。生成只含稳定 ID、内容地址和版本的索引。依赖重复出现时按真实资源归属合并到共享包，不能按名称猜测同一资源。源图与技能编辑器覆盖数据仍按原有版本和哈希校验。
2. 用同一内容接口驱动场景与技能编辑器。Editor 用 AssetDatabase 解析当前选择的施法者、目标和图。战斗运行时使用现有 `IAssetService` 和战斗 `BindingScope` 获取阵容涉及的资源。阵容未加载完不接受施放。离场、重开和加载取消先终止演出再释放句柄，切换时失败显示缺失 ID 或地址。
3. 优先在现有签名更新体系的 YooAsset 包内增设战斗角色组，一名角色一个逻辑资产地址，共享资源独立分组。实际 Bundle 粒度以构建报告确定，避免多角色共用特效和纹理被复制。现有 YooAsset 服务独占全局实例，不应为每个角色新建一个包所有者。编辑器与 Windows 性能诊断入口可暂时保留现有直接引用适配器，完成等价回归和目标平台构建后删除。
4. 第一阶段保留原共享 FMOD bank，先量化音频驻留和主线程耗时。选中角色的 `voiceBankAddress` 可用于延迟加载，但需先证明原 bank 的事件、采样与程序音频依赖可按组卸载。Windows 延续已验证原生库。Android ARM64 的原生 FMOD 尚无验收证据。

## 切换验收

- 对比拆分前后的实际 `BuildReport`／YooAsset 包清单，记录 Player 初始安装体积、单角色更新下载字节、共享依赖重复数和八人冷启动。分别报告编辑器预览与 Windows Player 的首次选角和施放 P95/P99、峰值内存和离场后的释放量。
- 以不同的八人阵容测试一次冷加载、一次重复换人、一次取消和一次依赖缺失。服务端规则、事件与资源地址索引分别验收。客户端用同一源图对比编辑器与 Player 的镜头、HIT、CUTIN 及音频。
- 验证旧场景无悬空引用，以及 Windows 和 Android ASTC／ETC2 发布物均能加载同版本资源。原生音频在相应设备单测，缺失必须可诊断。当前 Actions Windows 工作流上限 25 分钟，仅执行源码、协议、配置及内容检查。它未启用 Git LFS 下载，也不运行 Unity，逐角色图形验收需由本地或专用执行环境提供结果。
