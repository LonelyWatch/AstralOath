## 神器功能、存储与战斗

- 背包神器页接真实持有列表。支持全部／通用／职业筛选，等级／强化排序，查看卡面、星级、属性和效果、锁定、出售和强化。英雄详情点现在的原版六边形槽，打开可用神器，确认装备、替换或卸下。没有持有神器时沿用原版空板。装备和专属装备维持各自现有页面。
- 每位英雄一个神器槽，每件神器同时只可占一个英雄的槽。按区服与账号保存独立神器实例，同名可持多个，保存经验、突破阶数、锁定、来源；配戴关系使用英雄实例 ID。跨英雄移动先确认，服务端同事务完成移除与装备。锁定或已装备的实例不能作为强化／出售材料。神器强化石、金钱、知识粉末按服务端账本扣发；材料数量和出售返还按配表验证。
- +0 新神器，默认强化上限 +15。相同模板的独立副本或符合资格的专用材料突破一次加 3 级上限，最多 5 次至 +30。提升上限后仍需经验。每 3 个强化等级提高一级技能，属性和经验曲线从原配置校准。五星知识罐的可用范围按神器配置。首版建议神器容量直接给 400，英雄仍为 1000。国服公告中的 400 是可扩充上限，扩容商城不在首版。[国服 3 月 12 日更新](https://www.taptap.cn/moment/780477977375803207?group_id=429095)
- 角色配戴先更新详情属性预览。支持持有实例的战斗由服务端在开局锁定配装、强化、属性及效果配置版本。战斗使用纯 C# 的统一触发与结算，回放沿用开局快照。现有模拟战按模板构建标准阵容，建议保持当前规则，另提供带持有神器的测试战斗入口。战斗中复用角色身上的效果提示词通路，显示对应神器图标与名称；伤害分摊、反击、额外回合、治疗等需要覆盖触发顺序及禁止递归反应。
- 手动出售确认明确列出返还。录屏中重复英雄自动传送、神器自动出售属于单独可配置能力。首版默认保留每次抽到的独立实例，建议在第二阶段接入自动处理与对应回执、首次获得保护和账本，验清哪些重复会被处理后开放。

## 事务、断线和容量

当前 Server/Host/Inventory 及 010_player_inventory.sql 管理英雄持有，尚缺神器、钱包、召唤记录。拟在现有 MySQL 与区服会话之上补上神器实例、配戴、钱包余额／流水、免费用量、池版本、愿望单、保底、请求回执和召唤保管箱。召唤事务复用内部背包发放，上层按服务器规则生成结果。

- 客户端只提交池 ID、已看到的版本、抽取次数、支付选项和一次请求 ID。服务器重验池开放时间、余额、规则版本、免费次数和愿望单。入池模板须同时有星级、已验配表、可用资源、客户端能呈现的记录。概率详情与实际抽取共用服务器的同一池配置及整数权重。
- 锁定玩家区服相关记录，以单事务扣票或免费次数、按顺序判定每抽、刷新保底、发放物品并保存回执和流水。客户端收到账本变更以后的回执才开始演出。确认弹板因价格／池版本变更失效时，刷新后需要再次点击确认。
- 同一请求 ID 同参数只发一次，重试取原回执；不同参数重用同 ID 明确报冲突。断线、关窗、跳过、重新上线都能拿回已确定的结果。NEW 以抽取顺序及实际首次获得记录为准，同抽出现两次同名时只在首次显示。
- **容量方案建议。** 抽前在背包和保管箱组合里预留整批可能需要的槽位，多出的结果进入可领取的保管箱，可按英雄／神器筛选，再领入背包；组合容量也不足时整批拒绝且不扣费。简化方案是抽前要求英雄栏和神器栏各留出本批最多数量，展示空间不足提示；它省去保管箱实现，但容易在空间不足临界点阻断十连。两种方案都在观察结果之前处理容量，避免反复请求改变实际出率。原包存在 gacha_inven.csb 和 gacha_inven_move.csb。
- 开发服仅使用真实的测试票券余额，建议新开发访客每区服一次性发 60 誓约书签和可完成一轮强化的测试材料。正式账号发放量、渠道与刷新时点待审核。现有三名初始英雄不通过召唤补发。首版范围包括票券扣除与养成消耗，真钱支付和商业礼包为独立事项。

## 审核后实施顺序与验收

1. **定版图鉴、配表、素材。** 在 Config/Schema、Config/Tables 补神器、效果、成长、卡池、候选与票券配置，走 Luban 生成。每件验中文名、原版 ID、职业、稀有度、卡面、成长曲线、效果分级和来源。先用测试固定概率总和、空池拒绝和原版素材映射，再接入前端。
2. **神器持有与养成。** 扩展 Server/Host/Inventory 及迁移，串起 Home/Scripts/HeroInventoryBinder.cs 和现有神器分页。验证同名两件分别强化和配戴、跨职业拒绝、跨实例移动、锁定、+15/+30 边界、重复提交及事务失败回滚。验证真实 MySQL 并重开客户端核对状态。
3. **战斗规则与显示。** 共享 Battle 模块实现生命周期、触发和数值。固定随机序列验低生命阈值、受击／攻击／非攻击／回合开始与结束、首领例外、同效果冲突、转移伤害及额外回合。以两端战斗和重放校验同一效果出现及一致。独立回归现有模拟战。
4. **召唤服务。** Server/Host/Summon 负责池读取、愿望单、抽取、回执和保管箱。新增测试覆盖首尾权重边界、免费刷新前后、120／121 次和十连中间命中重置、空池、过期池和组别缺资格、背包临界、同号重试、并发双开和断线重进。每种错误验证货币、库存、保底和日志一致。
5. **原版召唤界面。** 接通 HomeMoreMenuBinder 和 StartupNavigation，按项目 View、Binder、BindingMap 约定生成预制体。复用 GameText、GameButton、资源加载和关闭取消范围。对照录屏按 16:9 与手机宽屏取图，逐帧验确认弹板、蓝／金按钮、英雄／神器两种揭晓与各稀有度过渡、跳过、结算卡、详情及再召唤。实机确认抽到的英雄和神器在对应背包页可见。
6. **交付验证。** 运行服务端、Unity 图形验证和 Windows 两个客户端，回归上一版更多、英雄和背包。主页和召唤内容属于 Foundation 业务热更候选，先做现有母包的 AOT 兼容检查，再按平台构建签名热更。服务端和迁移单独验收。Android 原画幅、安全区、触摸与演出帧率记录实测结果。

## 审核时的四个决定

- **神器名单。** 是否接受 22／12／8 的首批及所列替选范围。
- **召唤首版。** 是否接受常驻誓约（含愿望单）＋伊赛丽亚／星辰之歌 UP，其他录屏卡池按后续阶段接入。
- **满仓处理。** 是否首版就做召唤保管箱，神器容量是否直接设为 400。
- **测试票券。** 是否接受开发访客每区服一次发 60 誓约书签，正式账号先仅开放每日 1 次免费抽及后续另行审核的获取渠道。
