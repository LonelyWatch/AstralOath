# 游戏内邮件系统设计

2026-11-22 · 设计稿 · 对照代码基线 `99c91b98`。本稿约定收件范围、发信操作、收件和领取流程。下文命令和游戏入口均为拟建功能。

## 玩家、开发 GM 和服务端分别能做什么

- **玩家**在大厅点信封，查看本区自己的邮件，阅读正文、领取附件。离线时可以收到邮件。换设备登录后能看到相同的阅读和领取状态。
- **开发版 GM** 增加「邮件」模块。所有能使用开发 GM 的登录账号都可以给自己发一封真实的游戏内邮件，覆盖从提示角标到领取入账的完整路径。
- **服务端运营人员**可以按一个或多个玩家 ID、白名单、指定区服发送。每种范围都允许叠加黑名单。用一份补偿模板就能向不同名单发信，各批可独立查进度。

## 服务端怎样发一封信

拟在 `Server/Ops` 提供 `Mail.ps1`。直接运行进入中文交互模式，选环境和区服 → 填标题、正文或载入模板 → 选附件 → 选收件人 → 查看预览 → 确认后取得批次号。操作者可以在服务器本机完成这条流程，无需手写 SQL、重启游戏服或登录游戏。相同能力也提供给脚本调用。

```powershell
# 以下为拟定的操作接口。$playerId 为本区稳定玩家 ID，名单为 UTF-8 文本，每行一个 ID。
.\Server\Ops\Mail.ps1 preview -Realm undying-memory -To $playerId -Template .\maintenance.json
.\Server\Ops\Mail.ps1 preview -Realm undying-memory -AllowFile .\affected.txt -DenyFile .\compensated.txt -Template .\maintenance.json
.\Server\Ops\Mail.ps1 preview -Realm undying-memory -AllInRealm -DenyFile .\excluded.txt -Template .\maintenance.json

# preview 返回 previewId 和人数。confirm 绑定这次预览，status 可在终端关闭后查询。
.\Server\Ops\Mail.ps1 confirm -PreviewId $previewId
.\Server\Ops\Mail.ps1 status -BatchId $batchId
```

模板示例对应一封可领取 5 个誓约书签的信。服务端从现有目录校验奖励标识和数量，载入后可在预览中看到中文名称。标题或正文使用纯文本。

```json
{
  "title": "维护补偿",
  "body": "维护已结束，感谢你的等待。请查收随信附上的誓约书签。",
  "expiresInDays": 7,
  "attachments": [
    { "kind": "currency", "key": "bookmarks", "quantity": 5 }
  ]
}
```

### 谁会收到

1. 每批明确选定区服。先选一个基础范围：指定玩家（`-To` 接受一组 ID）、白名单文件、或显式的全区。黑名单从该范围中扣除，优先级最高。**只给黑名单时，操作员须显式选择“全区排除名单”**。无基础范围、空白名单或名单文件无法读取，均不可提交。
2. 以区服和稳定玩家 ID 去重。白名单含甲、乙、乙、丙，黑名单含乙，结果为甲、丙各一封。丙离线也会收到。预览显示基础人数、重复数、命中排除数、实际人数以及未识别或跨区的 ID。遇到无法解析的输入，先修正名单再生成预览。完整排除得到零人时可查看结果，发送按钮不可用。
3. 整区范围建议定义为**预览时已进入该区的注册玩家**，包括离线玩家。预览后首次进区的玩家不补入本批。现有版本固定一个区 `undying-memory`。实施时在选服成功事务内记录持久的区服成员关系。单区存量可用 `entry_account.arena_expires_at IS NOT NULL` 回填曾进区的注册账号，过期时间早于今天也应纳入。迁移前后用选服审计核对。开发环境允许的旧游客会话可给自己发测试邮件，运营整区名册默认只含注册玩家。[现有选服入口](../../Server/Host/Entry/EntryEndpoints.cs) · [成功选服的存储与审计](../../Server/Host/Entry/EntryStore.cs)
4. 预览保存最终人员名单、标题正文、奖励明细、区服和有效期规则。确认页给出区服、实际人数、单人及合计奖励。名单或模板有变更需另行预览。每个预览最多创建一个批次，重复确认或终端超时后再次确认，返回同一批次号。
5. 状态页给出目标数、已投递、待投递、投递失败及其原因，另外统计已领取数。例如「投递 80/80、领取 36/80」表示 80 人都可查信。分批投递中断后接续原批，仅补未完成的记录。

## 游戏内的操作

**玩家邮箱。** 进入大厅时取得邮箱摘要。点信封读取列表，阅读正文与领取附件分别持久化。附件列出名称、数量及领取状态。点领取后，以服务端回执更新附件、背包、货币及角标。纯文字邮件可直接阅读。角色或装备容量不足时，整封信的附件继续保留，提示需要腾出的背包，整理后可以重试。全部领取对当前快照中符合条件的邮件逐封处理，汇总成功和未领的原因。正文在哪一层展示、领取后停在哪一页，按原版实录确定。

**角标。** 服务端分开返回未读数和有待领附件的邮件数，均排除已过期邮件。另提供“未读或待领”的去重数，一封最多计一次。参考只能确认信封有独立数字角标，读取、领取哪一步扣减要用同一封信的前后实录决定。信件以服务端 UTC 时间判断失效。建议普通补偿模板默认七天，发信可指定其他有效期。全批从运营确认时起计算同一个到期时间，预览显示有效期长度，确认回执打印确切到期时间。工作队列落后到整批过期时停止剩余投递并在批次状态标示。国服两次公告明确各自活动的邮箱奖励保留七天。[2024 年国服活动说明](https://www.taptap.cn/moment/552549847060710331) · [2026 年国服活动公告](https://www.taptap.cn/moment/864213749114864680)

**开发 GM。** 沿用 R34 的深色浮窗和模块导航。收件区显示当前区和登录角色，只读。选「无附件」或从现有调试奖励目录添加物品，设置数量和有效期，填写标题、正文。预览并发送后显示邮件编号，保留上次草稿便于修改复测。明确点击「再发一封」才创建新请求。GM 收到投递回执时只更新邮箱，随后玩家实际领取才改变余额与库存。收件人取自经过鉴权的会话。请求只含内容、附件、有效期和请求 ID。服务端拒绝传入其他玩家、白名单、黑名单、整区等目标参数。保持现有开发构建和回环开发服门槛。

## 在本项目怎样接入

1. **玩家协议与界面。** 在服务端新增游戏内 Mail 模块。注册验证码邮件继续走 Entry 的 SMTP。玩家接口提供邮箱摘要、按游标倒序分页、正文、标记已读、领取和账号事件流，均从登录身份与已选区服解析收件人。列表以投递时间和投递 ID 稳定排序。客户端以对应页面的 `WindowCoordinator` 打开同一个邮箱，返回时恢复原页面。业务归 Binder，开窗作用域随窗口关闭释放。各处信封共用同一账号摘要，页面入口的可点状态单独对照录像。
2. **存储。** 用 MySQL 8.4 保存区服成员、预览/发信批次（含不可变正文与附件快照）、冻结名单与投递状态、逐玩家阅读/领取时间、邮箱版本、请求回执。每个 `(batchId, realmId, playerId)` 最多一条投递，按 `(realmId, playerId, deliveredAt, deliveryId)` 查收件箱。每个附件有稳定序号。模板后续修改对已发内容无影响。已领取或过期后可按留存策略整理展示记录，防重键和账本须覆盖所有允许重试的期限。
3. **发信路径。** GM 的“给自己发一封”和运营的批次共用投递服务。运营脚本建议通过本机受操作系统 ACL 限制的运维管道调用 Host，仅获授权的服务维护人员可用。实际投递由 Host 执行。长名单分段提交，批次唯一键和逐人唯一键支持服务重启与重复确认。投递只产生邮件，附件在领取时入账。
4. **领取路径。** 预览时校验并冻结可实际发放的规格，含装备属性等会受改版影响的内容。如使用版本化目录，则保留该版本直到邮件都已失效。领取时在同一事务内锁定玩家及投递，校验归属、期限、容量与余额上限，按冻结规格更新库存、领取时间、回执及审计。货币按增量入账，同种可堆叠项先合并。独立装备、神器、英雄经现有库存流程生成实例和图鉴记录。首版只开放能完整入账的奖励。任何附件失败，整封回滚。相同请求 ID 和参数重试返回已提交回执，参数冲突返回冲突。同封换请求 ID 或收到并发请求，也只能发一次。已成功的领取即使重试时过期也返回既有结果。一键领取请求绑定稳定的邮件 ID 列表，逐封可重试。新到邮件留给下次操作。[现有装备回执与库存实现](../../Server/Host/Inventory/InventoryStore.Equipment.cs) · [现有材料账本](../../Server/Host/Inventory/InventoryStore.Artifacts.cs)
5. **在线与离线。** 投递、阅读、领取提交时同步增长邮箱版本并写入待发通知，事务成功后通知本区该账号的有效会话。连接初始即同步，断线重连按版本补取摘要或快照，丢弃重复或较旧通知。打开邮箱时更新列表，关闭邮箱时只更新角标，按最近到期时间或回到前台纠正过期数据。通知仅携带变更版本，慢连接合并为最新版本。多个 Host 各自通知本地订阅者。现有选服会轮换账号令牌，旧会话失效要关闭事件流，切换账号同时清空邮箱缓存。角色和背包缓存在领取成功后按受影响项更新。[房间订阅生命周期](../../Server/Host/Arena/ArenaRoomEventStream.cs) · [现有会话校验](../../Server/Host/Arena/ArenaStore.cs)
6. **审计与权限。** 将运营确认、开发 GM 自发、玩家成功领取与对应业务写入同事务记录。关联操作者、区服、批次或投递号、请求号。投递和领取计数从对应业务记录汇总。正文、标题、原始名单、令牌、账号联系方式不进入操作日志。名单明细只供有该区权限的操作人员查看。普通玩家请求必须校验每一封的归属。正式环境不给游戏客户端开放运营发信入口。[项目操作留痕规则](../development/operation-audit.md)

## 落地次序与验收

1. 用隔离的 MySQL 测单人、多选、白名单、全区减黑名单、交集排除、空名单、跨区、离线账号和旧账号回填。预览后新增账号、改模板或编辑原名单，实际收件人和内容仍等于已确认预览。
2. 在测试区操作服务端工具，从加载模板到查批次完整走通。模拟重复确认、终端中断、Host 在部分投递后重启。逐玩家核对收件数，同一批同一玩家只收到一封。
3. 开发 GM 用两个账号验证。甲自发后只在甲出现，乙不可读、领或代发。正式客户端隐藏入口，正式或非回环 Host 不注册 GM 路由。测试纯文本、货币和带容量限制的附件。检查入账前后余额、实例数及审计，覆盖同一有效会话并发领取、超时重试、背包最后一格竞争、过期边界和发送后装备改版或下架。
4. 两个客户端验证在线通知、断线补收、离线重登和换设备登录后已领状态一致。旧会话失效后中止订阅并停止接收。按补录逐项核对信封角标、列表、详情、奖励与返回。界面参考齐备后再验收原版视觉与声音。
