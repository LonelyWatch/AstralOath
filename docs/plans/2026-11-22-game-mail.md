# 游戏内邮件系统设计

2026-11-22 · 设计稿。玩家收件、领取、记录和音效已核对同版本实机。下文服务端命令、开发 GM 操作、存储和客户端接入均为拟建功能。[录像时间点、关键帧与缺失画面](../development/mail-ui-reference.md)

## 玩家、开发 GM 和服务端分别能做什么

- **玩家**在大厅点信封，查看本区自己的邮件，阅读正文、领取附件。离线时可以收到邮件。换设备登录后能看到相同的阅读和领取状态。
- **开发版 GM** 增加「邮件」模块。所有能使用开发 GM 的登录账号都可以给自己发一封真实的游戏内邮件，覆盖从提示角标到领取入账的完整路径。
- **服务端运营人员**可以按一个或多个玩家 ID、白名单、指定区服发送。每种范围都允许叠加黑名单。用一份补偿模板就能向不同名单发信，各批可独立查进度。

## 服务端怎样发一封信

拟在 `Server/Ops` 提供 `Mail.ps1`。直接运行进入中文交互模式，选环境和区服 → 填标题、正文或载入模板 → 选附件 → 选收件人 → 查看预览 → 确认后取得批次号。操作者可以在服务器本机完成这条流程，无需手写 SQL、重启游戏服或登录游戏。相同能力也提供给脚本调用。

```powershell
# 以下为拟定的操作接口。$playerId 为本区稳定玩家 ID，名单为 UTF-8 文本，每行一个 ID。
.\Server\Ops\Mail.ps1 preview -Realm undying-memory -To $playerId -Template .\maintenance.json
.\Server\Ops\Mail.ps1 preview -Realm undying-memory -AllowFile .\affected.txt -DenyFile .\compensated.txt -Template .\maintenance.json
.\Server\Ops\Mail.ps1 preview -Realm undying-memory -AllInRealm -DenyFile .\excluded.txt -Template .\maintenance.json

# preview 返回 previewId 和人数。confirm 绑定这次预览，status 可在终端关闭后查询。
.\Server\Ops\Mail.ps1 confirm -PreviewId $previewId
.\Server\Ops\Mail.ps1 status -BatchId $batchId
```

模板示例对应一封可领取 5 个誓约书签的信。服务端从现有目录校验奖励标识和数量，载入后可在预览中看到中文名称。标题或正文使用纯文本。

```json
{
  "letterType": "standard",
  "title": "维护补偿",
  "body": "维护已结束，感谢你的等待。请查收随信附上的誓约书签。",
  "expiresInDays": 7,
  "attachments": [
    { "kind": "currency", "key": "bookmarks", "quantity": 5 }
  ]
}
```

### 谁会收到

1. 每批明确选定区服。先选一个基础范围：指定玩家（`-To` 接受一组 ID）、白名单文件、或显式的全区。黑名单只从当前批次的基础范围中扣除。被排除的玩家保留原有邮件，可以接收其他批次的邮件，也可以在开发版给自己发测试邮件。**只给黑名单时，操作员须显式选择“全区排除名单”**。无基础范围、空白名单或名单文件无法读取，均不可提交。
2. 以区服和稳定玩家 ID 去重。白名单含甲、乙、乙、丙，黑名单含乙，结果为甲、丙各一封。丙离线也会收到。预览显示基础人数、重复数、命中排除数、实际人数以及未识别或跨区的 ID。遇到无法解析的输入，先修正名单再生成预览。完整排除得到零人时可查看结果，发送按钮不可用。
3. 整区范围建议定义为**预览时已进入该区的注册玩家**，包括离线玩家。预览后首次进区的玩家不补入本批。现有版本固定一个区 `undying-memory`。实施时在选服成功事务内记录持久的区服成员关系。单区存量可用 `entry_account.arena_expires_at IS NOT NULL` 回填曾进区的注册账号，过期时间早于今天也应纳入。迁移前后用选服审计核对。开发环境允许的旧游客会话可给自己发测试邮件，运营整区名册默认只含注册玩家。[现有选服入口](../../Server/Host/Entry/EntryEndpoints.cs) · [成功选服的存储与审计](../../Server/Host/Entry/EntryStore.cs)
4. 预览保存最终人员名单、标题正文、奖励明细、区服和有效期规则。确认页给出区服、实际人数、单人及合计奖励。名单或模板有变更需另行预览。每个预览最多创建一个批次，重复确认或终端超时后再次确认，返回同一批次号。
5. 状态页给出目标数、已投递、待投递、投递失败及其原因，另外统计已领取数。例如「投递 80/80、领取 36/80」表示 80 人都可查信。分批投递中断后接续原批，仅补未完成的记录。达到 100 封的玩家在本批标记 `mailbox_full`，从已投递计数中扣除。项目提供针对失败玩家的原批次重试，检查原有效期与当前容量，给原名单以外的人发信需另建批次。

## 游戏内的操作

### 收件、领取和记录

- **收件页**从大厅信封进入，展示收件与记录两个图标页签。邮箱内可查看附件信息。行末的绿色「领取」依据信件类型操作。普通奖励直接领取，蓝标 GM 信先打开带正文的详情，玩家点「收信」才发奖。详情与附件提示都可返回当前列表。
- **信封角标**和页脚容量共用本区当前玩家的有效收件数。打开列表、GM 正文或附件提示保持原计数，领取提交后每封减一。零封时隐藏信封数字，收件页显示 0/100、「没有可领取的邮件。」和置灰的「全部领取」。最多接收 100 封有效待收邮件。已入历史的邮件另计。
- **全部领取**只处理玩家确认时快照内的普通信。确认窗明示行动力等入场货币可超出持有上限，英雄或装备背包已满时略过对应邮件，同时略过 GM 信。取消保留所有邮件。只剩 GM 信时仍可打开确认，确认后弹出「无法使用全部领取的邮件。」。成功的普通信逐封写历史，奖励窗合并同种物品显示总数。项目对含多种附件的信采取整封处理，任一附件无法入账即保留原信。
- **奖励表现**按领取结果选择。单个普通道具可显示顶部蓝色奖励条，打开礼包后在横向「获得奖励」弹窗展示包内物品，全部领取在同类弹窗展示汇总。GM 信也可能发行动力或发礼包，领取入口与奖励展现分别由信件类型和附件决定。
- **记录页**按写入历史的时间倒序排列，普通已领灰色「已领取」，普通过期记录可显示灰色「已删除」。带蓝标的 GM 信可「再次查看」正文与附件，收信按钮呈灰色，重复操作只给出已领取提示。录像也展示了 GM 已过期历史信的正文。记录自保存日起最多显示 90 天，最多 100 条，先到的限制生效。
- **有效期**由服务端按 UTC 判断。普通补偿模板可设置七天，也可为其他时长。运营确认时固定全批到期时间，工具打印确切时刻。队列滞后到过期时终止剩余投递并显示原因。过期进入历史后不再占收件容量。

### 发信渠道和信件类型

服务端模板保存 `letterType`（普通 `standard` 或需要逐封收信的 `gm`）、发件人展示资料、正文、附件和有效期。收件人选择、作者权限及工具来源单独记录。客户端只从类型决定 GM 蓝标、正文、批量适用性和历史回看。实录中同一「GM亚卡」既有带蓝标的 GM 信，也有未带蓝标的普通维护信。

开发版沿用 R34 深色 GM 浮窗和模块导航。所有开发版登录账号均可给当前账号自发，区服与收件人只读。选择普通或 GM 信测试模板、填写标题正文，按目录添加附件并设置数量和有效期，预览后发送。发送回执只更新邮箱，实际收信后才更新余额与库存。使用独立请求 ID，重复提交返回同一封，显式「再发一封」才产生新邮件。Host 从已鉴权会话解析收件身份，拒绝携带其他玩家、名单或整区范围的自发请求。沿用现有开发构建与回环开发服门槛。服务端运营工具单独提供群发和名单管理。[开发 GM 样式参考](../../.artifacts/gm-r34/screens/inventory.png)

## 在本项目怎样接入

1. **玩家协议与界面。** 在服务端新增游戏内 Mail 模块。注册验证码邮件继续走 Entry 的 SMTP。玩家接口提供邮箱摘要、收件与记录的游标分页、正文和附件预览、单封与批量领取、账号变更通知。查信和领奖都从登录身份与已选区服解析收件人。收件按接收时间和投递 ID 稳定分页，记录按保存时间和投递 ID 倒序分页。客户端以对应页面的 `WindowCoordinator` 打开同一个邮箱，返回时恢复原页面。业务归 Binder，开窗作用域随窗口关闭释放。各处信封共用同一账号摘要，页面入口的可点状态单独对照录像。
2. **存储。** 用 MySQL 8.4 保存区服成员、预览/发信批次（含不可变正文与附件快照）、冻结名单与投递状态、每位玩家的投递、领取与进入历史时间、结局（已领或已过期）、邮箱版本、请求回执。每个 `(batchId, realmId, playerId)` 最多一条投递，按 `(realmId, playerId, deliveredAt, deliveryId)` 查收件箱。每个附件有稳定序号。模板后续修改对已发内容无影响。投递与领取在同一事务内分别锁定该玩家的邮箱行，先清理到期有效邮件再检查 100 封上限，避免并发超收。领取或到期时将该信移出活动收件列表并记入历史，历史仅展示最近 90 天内最新 100 条。展示记录整理不影响业务账本和仍可重试的防重键。
3. **发信路径。** GM 的“给自己发一封”和运营的批次共用投递服务。运营脚本建议通过本机受操作系统 ACL 限制的运维管道调用 Host，仅获授权的服务维护人员可用。实际投递由 Host 执行。长名单分段提交，批次唯一键和逐人唯一键支持服务重启与重复确认。投递只产生邮件，附件在领取时入账。
4. **领取路径。** 预览时校验并冻结可实际发放的规格，含装备属性等会受改版影响的内容。如使用版本化目录，则保留该版本直到邮件都已失效。领取时在同一事务内锁定玩家及投递，校验归属、期限和附件对应的入账限制（行动力等入场货币允许超过自然恢复上限），按冻结规格更新库存、领取时间、回执及审计。货币按增量入账，同种可堆叠项先合并。独立装备、神器、英雄经现有库存流程生成实例和图鉴记录。首版只开放能完整入账的奖励。任何附件失败，整封回滚。相同请求 ID 和参数重试返回已提交回执，参数冲突返回冲突。同封换请求 ID 或收到并发请求，也只能发一次。已成功的领取即使重试时过期也返回既有结果。一键领取请求绑定稳定的邮件 ID 列表，逐封可重试。新到邮件留给下次操作。[现有装备回执与库存实现](../../Server/Host/Inventory/InventoryStore.Equipment.cs) · [现有材料账本](../../Server/Host/Inventory/InventoryStore.Artifacts.cs)
5. **在线与离线。** 投递、领取或到期迁移提交时同步增长邮箱版本并写入待发通知，事务成功后通知本区该账号的有效会话。连接初始即同步，断线重连按版本补取摘要或快照，丢弃重复或较旧通知。打开邮箱时更新列表，关闭邮箱时只更新角标，按最近到期时间或回到前台纠正过期数据。通知仅携带变更版本，慢连接合并为最新版本。多个 Host 各自通知本地订阅者。现有选服会轮换账号令牌，旧会话失效要关闭事件流，切换账号同时清空邮箱缓存。角色和背包缓存在领取成功后按受影响项更新。[房间订阅生命周期](../../Server/Host/Arena/ArenaRoomEventStream.cs) · [现有会话校验](../../Server/Host/Arena/ArenaStore.cs)
6. **审计与权限。** 将运营确认、开发 GM 自发、玩家成功领取与对应业务写入同事务记录。关联操作者、区服、批次或投递号、请求号。投递和领取计数从对应业务记录汇总。正文、标题、原始名单、令牌、账号联系方式不进入操作日志。名单明细只供有该区权限的操作人员查看。普通玩家请求必须校验每一封的归属。正式环境不给游戏客户端开放运营发信入口。[项目操作留痕规则](../development/operation-audit.md)

## 落地次序与验收

1. 用隔离的 MySQL 测单人、多选、白名单、全区减黑名单、交集排除、空名单、跨区、离线账号和旧账号回填。预览后新增账号、改模板或编辑原名单，实际收件人和内容仍等于已确认预览。
2. 在测试区操作服务端工具，从加载模板到查批次完整走通。模拟重复确认、终端中断、Host 在部分投递后重启。逐玩家核对收件数，同一批同一玩家只收到一封。
3. 开发 GM 用两个账号验证。甲自发后只在甲出现，乙不可读、领或代发。正式客户端隐藏入口，正式或非回环 Host 不注册 GM 路由。测试纯文本、货币和带容量限制的附件。检查入账前后余额、实例数及审计，覆盖同一有效会话并发领取、超时重试、背包最后一格竞争、过期边界和发送后装备改版或下架。
4. 两个客户端验证在线通知、断线补收、离线重登和换设备登录后已领状态一致。旧会话失效后中止订阅并停止接收。对照 11 月 22 日实录验收 15→14、五封混合全部领取后剩两封 GM、两封 GM 再次全部领取维持 2、逐封查看和领取后 2→1→0、最后返回大厅无角标。核对顶部奖励条、礼包窗、历史逐封明细及开关音。
5. 补做 99 封时两个批次同时投递、100 封时原批次重试、入场货币越自然上限、满背包邮件在下一次成功领取、90 天和 100 条两个历史边界。验收发信名单时，证明被排除的玩家仍能正常接收另一批次。画面尚缺的边界须分别标记为逻辑通过与画面待核。
