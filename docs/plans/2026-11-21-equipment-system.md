# 普通装备系统调研与实施方案

2026-11-21 · 待实施。首个可玩目标是让玩家获得一件装备，在英雄页换上它，看见可解释的面板变化，并带着这份面板进持有英雄试战。装备库存、产出、随机结果与战斗入场值由服务端决定。统一面板的模拟战继续使用房间原有规则。

## 原作规则与取证

本次查阅的是项目固定的 `pack-15-r4262`。原包 `text/zhs/text.db` 的 SHA-256 为 `4b95b899ae5042ad90c6eb0009451547e727a1413f848c74933f6ffac4c6e114`。本机可在 `.artifacts/roster-data/text.zhs.json` 按下列键复查，导出文件 SHA-256 为 `723a4426b761a6e4ce80f7e85aeb930b023cbacdecf278be37435bfd4cf33301`。数字取自固定版本，网页活动另标日期。[项目来源记录](../../Config/BattleText/original-zhs.json)

| 武器 | 固定攻击力数值 | 无防御力数值或防御力百分比 |

上表列出能从帮助直接确定的限制。右侧三件完整的普通属性池、数值与百分比的权重，仍须逐行核对后导入。核查键为 `help_infoinve2_3_1_desc`、`txt_equip_excluded_sub_desc_weapon`、`txt_equip_excluded_sub_desc_armor`。所有部位都排除与主属性同类型的副属性，见 `txt_equip_random_option`。筛选和配表都应区分“攻击力 +40”和“攻击力 +8%”。

- **物品等级、品质与强化阶段是三个字段。** 普通等级不会随强化提升。一般、高级、稀有、英雄、传说品质在 +0 时分别有 0、1、2、3、4 条副属性。主属性每升一级提高，+3、+6、+9、+12、+15 分别新增或提升一条副属性，+15 时共有四条。具体哪一跳新增由品质与阶段表决定。材料包含适用的强化石和强化粉末，并消耗金币。强化石须与部位适配，出售返还的强化粉末随物品等级和强化阶段提高。核查键为 `help_infoinve2_1_1_desc` 至 `help_infoinve2_4_1_desc`、`ui_unit_item_upgrade_desc`、`guidequest_category_33`。
- **套装分为面板效果和战斗效果。** 速度套装为速度提升 25%，暴击套装为暴击率提升 12 个百分点。免疫套装在开战时给自身 1 回合免疫，同类效果有叠加限制。反击套装在受击时有 30% 几率触发。对应原文键为 `set_speed_de`、`set_cri_de`、`set_immune_de`、`set_counter_de`。Fribbels 的公开实现可交叉检查件数，如速度四件、暴击两件。发版用固定源目录核对件数与可叠层数。[Fribbels 套装与件数定义](https://github.com/fribbels/Fribbels-Epic-7-Optimizer/blob/main/app/js/lib/constants.js)
- **产出决定后续资格。** 钢铁工坊按讨伐材料选装备池，例如双足飞龙对应暴击、命中、速度。符合来源的 Lv.85、+15 装备可重铸为 Lv.90，一件仅一次，副属性提升量与各条强化次数有关。+15 后可用转换石改一条副属性，后续转换绑定同一条。再次转换成相同类型时，新值至少保留现值。可复查 `help_infoinve2_5_1_desc`、`ui_reforge_main_desc`、`ui_unit_item_change_desc`。国服 2026 年 3 月定制活动则产出不能重铸的 Lv.88 装备，活动可以手选强化项。这两条路径应配置为不同来源。[国服运营团队活动规则](https://www.taptap.cn/moment/785945272768269860)

## 项目接入点

英雄详情已经摆好六个固定装备槽。通用组件能显示空槽、物品图、强化等级与通知角标。普通装备背包目前显示空状态，已接通的神器另有实例、材料与接口。两套库存可以共用控件、金币与事务模式，各自保留品类、容量、材料 ID 和战斗效果。专属装备的英雄限制与技能变体留作单独扩展。[主页与背包](../../Assets/Game/Modules/Home/README.md) · [EquipmentSlotBinder](../../Assets/Game/Common/EquipmentSlotBinder.cs) · [神器事务](../../Server/Host/Inventory/InventoryStore.Artifacts.cs)

**装备穿在英雄实例上。** 同账号两只同模板英雄分别有自己的六槽。持有英雄试战已按实例读取等级、星级和神器，可在这条读取路径一次加入装备。默认模拟战的选禁提交模板 ID 并由服务器生成统一面板。以后如增加自有装备房间，创建房间时明确规则，选人时提交持有实例并校验归属，开场后双方都绑定同一快照。[英雄实例约定](../architecture/adr/017-hero-inventory-identity.md) · [持有编队读取](../../Server/Host/Inventory/InventoryStore.Trial.cs) · [模拟战入口](../../Server/Host/Battle/ArenaBattleCatalog.cs)

## 装备从生成到出售

1. **生成。** 掉落或奖励先提供服务端来源流水 ID 和掉落池。按配方确定部位、等级、品质、套装，抽主属性，再从部位与主属性允许的池无放回抽取副属性类型及初始值。写入时保存来源、配置版本、具体数值和每条副属性的位置。固定奖励允许作者直接给出合法词条。首版用测试账号的固定奖励验证整条路径，正式掉落由之后接通的玩法发放。
2. **穿脱与替换。** 从服务端报价取得新旧实例、需要解除的装备、费用及换装后面板。确认时在一次事务中完成扣费、移走旧件、绑定新件；已穿在另一英雄上的装备需明确显示原佩戴者。费用或库存版本改变时刷新报价。拟定首版锁定仅保护出售、提取和充当消耗品，保留穿戴能力。满包时按确定的占格规则计算事务前后净增量，换装失败不留空槽。
3. **强化。** 客户端选择材料与数量，服务端校验归属、可用材料、金币、经验、上限，再逐个跨过本次达到的阶段。一次从 +2 到 +7 必须依次处理 +3、+6 并记录两次结果。每条保留初始值、命中次数和实际增量，供重铸、展示和追账。若启用经验暴击或溢出返粉，使用固定版对应曲线，账本内一同结算。强化动画只播放回执。
4. **锁定、出售和提取。** 有锁或已穿戴的物品不进入批量出售候选，服务端再次检查。出售预览列出金币及粉末，提取另用独立产物表。批量命令先完整校验所选集合，再统一扣件和发放。二次确认展示数量和收益。

## 数据、接口与事务

- **配置。** 在 `Config/Schema/equipment.xml` 和 `Config/Tables/` 增加模板、部位主副属性池、品质分阶段规则、强度区间、经验费用、套装、来源及配方。导入前核对只读目录 `D:/sevenepic/原始资源/db/` 的 `equip_item`、`equip_stat`、`item_equip_stat_count`、`item_equip_balance`、`item_equip_upgrade*`、`equip_item_undress`、`item_equip_substat_change*`、`skill_equip` 等原表。记录表哈希、字段映射和样本，不把原包提交到仓库。用 Luban 生成端服同源目录与哈希，校验权重、引用、跨阶段条数及区间。[配表与生成](../../Config/README.md)
- **存储。** 在现有迁移目录追加迁移。建议新增装备实例、实例副属性、英雄装备槽、请求回执四张明细表。在玩家与区服对应的背包头增加独立的装备容量和单调递增的装备版本。每次新增、删除、改词条或换槽均在同一事务将版本加一。实例含 `instance_id / player_id / realm_id / template_id / set_id / item_level / grade / xp / main_stat / locked / revision / source_ref / rules_version`。副属性以实例和位置为主键，存实际数值、强化记录、已转换位置；槽表唯一约束为“归属＋英雄实例＋部位”和“归属＋装备实例”。复合外键分别约束英雄、装备归属；部位同时由写入口核验。背包容量独立配置。老账号迁移后普通装备初始为空。
- **接口。** 建议 `GET /api/inventory/equipment` 返回容量、占用、版本、实例与槽位。`POST /api/inventory/equipment/preview` 预览换装差值、费用或出售收益。`POST /api/inventory/equipment/actions` 传请求 ID、动作、装备/英雄实例、材料数量与预期版本，返回本次变更物品、槽位、钱包、面板和新版本。从认证上下文取账号，沿用服务端固定的 EntryEndpoints.RealmId。未来多区服按已验证的选服凭证绑定区服。客户端传入的面板、词条结果、价格、拥有者均不能作为结算依据。
- **双开与重试。** 复用现有 `LockInventoryOwner` 的玩家锁序与 MySQL 事务。先查请求指纹及回执，再验库存版本，保证网络中断后用同一请求重试可取回原结果。相同请求 ID 携带不同参数返回冲突。多件奖励以「来源流水＋奖励序号」唯一，同一批次重试复用原回执。扣费、发放、词条随机结果、库存修订、回执与操作审计同事务。第二个客户端使用过期版本时刷新并保留当前英雄选择。库存随机与对局随机使用各自的状态。[现有材料账本与迁移](../../Server/Host/Foundation/Migrations/013_summon_wallet_materials.sql) · [操作留痕](../development/operation-audit.md)

## 面板与战斗

在共享纯 C# 层新增装备面板计算，输入为成长与觉醒得到的裸面板、六槽词条和套装，输出八项 `BattleStats`、生效套装和面板分项。百分比沿用万分比整数，成长、装备、神器和战中增益各保留独立来源。现有 `BattleUnit` 已单独加入神器攻击和生命，接入时检查只计一次。[成长公式](../../Shared/com.astraloath.shared/Runtime/Battle/HeroStatCalculator.cs) · [战斗单位](../../Shared/com.astraloath.shared/Runtime/Battle/BattleUnit.cs)

首版拟按“基础值 ×（1＋装备和套装的同项比例之和）＋固定加成”计算攻、防、生命、速度；暴击等概率属性按百分点加算。取整顺序、神器参与百分比的范围及属性上限，发布前用原作面板跨整数边界核对。可先写两个明确的实现样例。裸速 100、速度四件、鞋子固定速度 +40，候选公式预期 165；裸暴击率 15%、暴击两件预期 2700 bp。卸掉一件速度装应只撤去相应的词条与套装效果。

反击、免疫、吸血等套装接入共享战斗事件。开战免疫在进入首回合前建立状态，反击走既有受击／反应窗口，沿用禁止反击、触发优先级与循环保护的规则。每种套装都有独立战例后再放入产出池。持有试战入场时一次读取六槽与神器并固定最终数值、套装效果、规则版本和内容哈希。重连与回放读取同一场次快照。战斗期间另一客户端换装只影响新场次。当前 ReadTrialFormation 在字典中为每位英雄执行一次 Add，再构造仅持有模板、成长与神器的 BattleOwnedHero，觉醒值现为 0。建议一次读取英雄与神器、再批量读取其装备明细，按英雄实例分组并保留请求顺序；同模板不同实例分别固定。持有试战的 matchHash 目前只含战斗和神器目录，需一并加入装备目录哈希。场次另存实例与实值用于复现。[试战入口与哈希](../../Server/Host/Battle/OwnedBattleTrialEndpoints.cs)

## 页面与首登缓存

英雄详情沿用页面内的 `EquipmentSlot.prefab`，有物品时显示物品图和 + 等级，空槽显示部位图，通知红点按独立业务条件点亮。背包装备页使用固定预制展示筛选、滚动网格、详情、锁与操作区。点击装备槽时默认过滤该部位，比较窗并排显示旧件、新件、套装变化、金币及八项属性差值。强化页分别显示物品等级、+阶段及将跨过的副属性节点。余额不足时允许点确认并显示原因。宽屏、窄窗下让底框、图标、等级和红点共用槽位父节点。[主页 Binder](../../Assets/Game/Modules/Home/Scripts/HeroInventoryBinder.cs) · [UI 约定](../development/ui-binder.md)

在登录到主页的黑屏期，将装备快照与现有英雄、神器并行读取，首屏必要图标预热，其余按可视区加载。按账号、区服与版本缓存，切英雄、背包、竞技场与战斗返回均复用。成功写操作应用增量，回前台、重连或写入冲突时带已知版本做轻量校验，在版本变化后重新拉取，登出或切区清理。页面关闭取消尚未完成的显示任务，已提交的服务端请求可按请求 ID 找回结果。已有「一键配戴」「全部解除」适合共用批量报价与一次提交。一键配戴先按玩家选择的属性和套装约束生成候选，列出六个变化槽、受影响英雄和净费用，再由玩家确认。

## 分期与验收

| 阶段 | 首个可交付行为 | 必须通过的验证 |
| --- | --- | --- |
| 1 · 六槽与静态套装 | 测试奖励入库，包内能看、穿、换、脱，详情和持有试战使用同一面板 | 同模板两只英雄分别穿装。六部位只收合法物品。两端抢同件只有一次提交。原有神器及统一面板 RTA 的基准不变 |
| 2 · 强化与流转 | 实际扣费、跨节点强化、锁定和出售，入口能处理余额不足 | 按五个品质逐阶段测试至 +15。重复请求、断网恢复、满包、已锁、已穿、跨区和任一扣费失败都要核对库存与账本 |
| 3 · 产出与战中套装 | 开放已核实的掉落或工坊配方，并逐项开放战中套装 | 固定随机样本检查池和边界；反击、不能反击、免疫驱散、同类套装叠加与回放重算各有战例 |
| 4 · 后续养成 | 依来源加入提取、重铸、转换和配装预设 | Lv.85 +15 的合法来源仅可重铸一次；活动 Lv.88 拒绝；转换锁定已选词条位置，同类型重转不降值，原有强化次数可追溯 |

先为各阶段写失败用例，再实施。在 `Server/Tests` 运行纯规则和使用独立 MySQL 库的事务用例；在 Unity 运行背包 PlayMode、普通及异形宽高比的截图对比；最终以两份原生客户端复验互换、断线、快速切页、进战与重连。发版顺序为兼容数据库迁移、服务端、签名客户端内容、开放相应来源。降级时先关闭对应写入口并保留已生成实例和账本。[服务端](../../Server/README.md) · [客户端分发](../development/hot-update.md)

**实施前待定的数值**包括普通装备占格和初始容量、逐品质逐阶段的新增／提升表、强化石与粉末的适配和经验曲线、拆卸费、随机权重、重铸白名单及百分比取整。用固定包一条可定位的源记录和一组实际输入输出落定每项。文档中的接口、迁移和里程碑均为拟议设计。
