# 模拟战选禁与入场

从 GameHome 进入竞技场，创建「基本」房间。默认每边预禁 2 人、房主先手、第三手禁用保护开启。房主可从房间顶部设置预禁人数 0–3 或开关保护，在参战席下方切换先手。双方都拥有当前服务器战斗目录里的英雄。第二个独立客户端入房后，当前客户端由客席点「准备」，房主可开始战斗，两个席位自动进入选禁。房主可以在两个座位上直接选择其中一个先选。先手真正改变时，服务端在同一事务内保存设置、清除房间准备并写入一条系统聊天提示。重复点已勾选的一方时继续保持原状态。预禁数量和禁用保护发生变化时也各发一条设置提示并重置准备。新版本服务端先应用 `008_arena_room_ready.sql`，房间响应通过 `supportsDraftReady` 声明准备端点可用。

- 预先禁用同时进行。选择满房间人数上限后提交；双方提交后公开结果。上限为 0 时直接进入选人。
- 选人顺序从先手开始为 1／2／2／2／2／1，双方各选五人。单选窗口 30 秒，双选两手共用 60 秒。已经选用或预禁的英雄会锁定。目录滚动结束会吸附到合法候选，预选头像在双方对应空槽闪烁，观战中的对手也在中央看到当前预选英雄的立绘。锁定后以已选立绘接续。待选框按各槽原版附件尺寸贴合底板，我方蓝色、对方红色，点击「选择」才锁定英雄。锁定后每个新槽只播放一次原包确认特效，中央立绘在不中断待机的情况下上跳并沿角色轮廓短暂白闪。收到同一版本的预选状态时沿用待选呼吸。预禁确认后暗显原版「选择」，对方决策时按钮保留淡绿底和箭头并显示「等待中」。
- 最终禁用同时进行。每边选择一个对手英雄，开启禁用保护时第三手不可禁。此阶段中央起始为空，选择敌方后显示灰暗立绘并压暗对应卡面。终禁确认播放原包中央 BANNED 和延迟 100 毫秒的粒子，等待时保留灰暗预览。加色光不写入覆盖透明度，原生金色火星保持亮度，宽雾光单独降亮。双方公开结果进入阵型时，两个被禁用的卡槽在原章位同步播放按约三分之一缩放的同源效果，最后显示红章。阵型确认后底部按键变暗并显示「等待中」。
- 阵型使用剩余四人。按 P2 7:24–7:27 对照，模型显示面绕原脚点放大 50%，保留四个蓝色圈位、换位交互和对宽大模型的边缘限制，同时提高预览纹理分辨率。点击两个站位交换，再按战斗开始确认。选人开始后预载闸门和战斗场景，场景根保持隐藏。服务端确认锁定一名英雄后，才把该英雄的战斗骨骼加入后台预解析队列，每个场景同时最多处理两份。离开选禁时停止等待并释放预载；阵型确认时用权威快照核对最终八人并补齐未准备的资源。联机场景不会解析本地演示阵容。最终确认后并行请求权威对局快照。门全关后接管并校验场景，角色和场景准备好才开门。开发日志 `ASTRAL_ARENA_LOADING` 分别记录场景、首个请求、门后等待与场景安装。带热缓存的本地 Unity Editor 联机回归中，关门后到准备开门约 1.16 秒，旧初始化路径测得约 12.04 秒。新解析入口属于 AOT，本轮没有 Windows 独立 Player 复测结果。站位按战斗场景的前、下、上、后顺序发送，阵型界面的实际位置与战斗一致。双方确认后闸门关合遮住加载，打开后本方站定并显示感叹号，敌方从右侧场外沿地面先后跑入。双方入位后镜头平滑拉近，入场和 IGNITION 完成后开放回合操作。以用户提供的 16:9 开场和开战帧为基准，分别对齐决斗场背景裁切及联机角色脚点。过渡约收近 15%，镜头小幅下移，超宽屏保持相同的垂直取景。

## 服务端与发布

`POST /api/arena/rooms/{id}/draft/settings` 允许空闲基本房的房主单独修改任一设置，并在同一事务内打点。

`POST /api/arena/rooms/{id}/draft/preview` 接收 `draftId`、`version`、`heroId` 和递增 `sequence`。只有当前选人席可以发送合法预选，双方读取 `previewHeroId` 和 `previewSequence`。预选仅随本次选人版本存活，超时、锁定或切换手次后清空，不推进回合或消耗选人次数。

[P2 4:24 附近](https://www.bilibili.com/video/BV1n7x96DETN/?p=2&t=264)逐帧核对：蓝侧锁定后卡槽内白闪约 0.15 秒，随后卡面先恢复，细蓝边和亮点晚于卡面消退。同一录像 4:12 附近的对手锁定对应暖白闪、红橙边缘和亮点。五个槽共用这套合成方式；侧槽材料的加色层只叠亮度，正常层负责透明覆盖。源轨道的卡面、双层亮边与时间键保留，转换时仅按卡槽显示范围缩小宽泛光，外缘及目录侧用透明渐隐。源贴图不改，原包 CFX 粒子保留亮点并压低低透明度外晕。

确认槽、中央禁用印章及粒子通过 `Tools/Arena/ImportDraftFeedback.py --check` 复核 42 项源文件和产物。更新日志保留原资源与生成物的各自校验值。已确认状态重连时保留结果，播放由权威选禁增量触发。局内骨骼使用同一个母包 Shader，但新参数默认关闭，须以新母包交付；旧版 Windows 包不会改变。

选禁与对局权威在服务端。事务锁定同一个房间。客户端按版本提交，使用请求 ID 去重，并限定为当前选禁 ID 或对局 ID。不同席位的同阶段提交可并行，禁名和站位在对手端按阶段公开。超时由当前两席的读取或操作推进，服务端从合法候选中选择；退出或席位活动过期会取消该次流程。战斗命令和配置摘要用于重连与回放。普通房间成员可以留在房间，观战入口尚未实现。

开发运行前应用迁移 `006_arena_draft.sql`、`007_arena_preban_three.sql` 和 `008_arena_room_ready.sql`，重新启动服务。Foundation 母包只内置 GameHome。战斗场景和转场配置包含热更新程序集定义的 Unity 脚本，必须在程序集就绪后从当前 Foundation YooAsset 包加载。0.1.9 在选位后因 Unity 无法恢复内置转场资源的字段而卡住，需安装更新后的母包以获得 AOT 场景加载服务。BP 窗口与角色素材目录随 Foundation YooAsset 包发布，进入 BP 时才读取角色预览资源。新增英雄时同步 BattleScene 战斗目录和原版卡面素材，再运行 `Tools/游戏主页/生成主页和模拟战` 生成对应目录和预制体。其他规则仍可保存和加入房间，联机开局目前只开放「基本」。实机录像对照图须经用户确认后才构建客户端安装包。

## 验收和待核对

MySQL 集成 244 项通过，Unity 图形 PlayMode 覆盖房间、选禁、双方独立会话、四个具体站位、银蓝闸门、八名角色入场与战斗事件同步。截图来自 Unity 编辑器实机，横屏包含 16:9 与 21:9。局内已接入服务端权威回合截止时间及原版红蓝圆形计时格：双方演出（含回合入场）就绪后开表，超时执行合法默认动作。30 秒为可配置项目策略，尚未核实为录像全部模式的原作时长。最新界面、IGNITION 和回合计时验收见[画面修订记录](../delivery/2026-11-15-draft-visual-revision.md)。阵型配置、禁用揭示和开场时序仍待用户截图审核。

## 本机复现

```powershell
$env:ASTRAL_ARENA_TEST_URL = 'http://127.0.0.1:7728'
pwsh -NoProfile -File Tools/Invoke-Unity.ps1 -Mode PlayMode -Graphics -TestFilter 'AstralOath.Client.Tests.ArenaDraftOnlineTests|AstralOath.Client.Tests.ArenaBattlePlaybackTests|AstralOath.Client.Tests.GameHomeArenaTests'
```

Windows 开发包另跑 `Tools/Test-WindowsArenaBattle.ps1 -Player <解压后的 AstralOath.exe>`。脚本以两个独立访客通过本机服务完成预禁、选人、终禁和阵型，再由打包后的 Player 运行实际入场代码，检查八个角色模型、服务端回合计时及首条战斗命令。该入口只对显式请求的联调包开放，服务地址必须为回环地址。Windows 成品验收还会在正式选人前让房主和客席分别发送一次预选，由另一席读取相同英雄，并确认不推进版本、不提前锁定，正式选人后清空。脚本在图形 Player 启动前完成此协议检查；对手红槽、闪烁和中央立绘由 Unity 图形 PlayMode 回归验证。

0.1.13 若出现「自己看得到预选，对手只有空红框」，先检查客户端实际连接的进程。服务端健康探针返回 200 只表明服务与数据库可用。旧服务可正常进入 BP 和正式选人，但真正的预选 POST 返回 404；配套服务对同一路径的无登录 POST 返回 401，表示该接口存在且需要登录。应使用同批次的客户端和服务端发布物，备份原库、用迁移账户应用缺失的 006–008，再以原运行账户切换至新版进程。切换后用新房间验证双方预选，避免把旧对局状态带入验收。该问题无需重装 0.1.13 客户端。
